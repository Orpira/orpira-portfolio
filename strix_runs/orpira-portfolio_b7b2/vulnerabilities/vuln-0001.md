# Rate-limit bypass in public contact endpoint via spoofed forwarding headers

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-08-26 13:44:54 UTC
**Target:** OrPiRa portfolio application
**Endpoint:** /api/contact
**Method:** POST
**CWE:** CWE-807
**CVSS:** 5.3
**Fix Effort:** Low

## Description

The public **`/api/contact`** endpoint derives its rate-limit key from client-supplied forwarding headers, allowing an unauthenticated attacker to evade the intended spam throttle by changing **`X-Forwarded-For`** or **`X-Real-IP`** values. This keeps attacker-controlled requests flowing into the service-role-backed contact ingestion path despite the presence of a limiter.

## Evidence

Dynamic validation showed that one spoofed address hit the configured threshold and a new spoofed address immediately restored access:

```http
POST /api/contact HTTP/1.1
Content-Type: application/json
X-Forwarded-For: 203.0.113.50
```

The downstream **`500`** responses came from the local Supabase insert environment, but they still prove the request passed the limiter and reached the service-role-backed processing path.

## Impact

An unauthenticated attacker can bypass the contact form's anti-automation control and continue submitting arbitrary lead data into the CRM ingestion flow by rotating spoofed IP headers. This permits unauthorized manipulation of CRM records at scale and defeats the endpoint's intended abuse-prevention boundary, even though the downstream insert path is protected only by server-side service-role credentials.

## Technical Analysis

The contact ingestion route calls the limiter with **`getClientIp(request)`** before inserting into Supabase:

```ts title=src/pages/api/contact.ts startLineNumber=95 endLineNumber=95
		if (isRateLimited(getClientIp(request))) {
```

The shared helper used for this decision trusts attacker-controlled headers:

```ts title=src/lib/rate-limit.ts startLineNumber=34 endLineNumber=53
export const getClientIp = (request: Request) => {
	const realIp = request.headers.get("x-real-ip")?.trim();
	if (realIp) {
		return realIp;
	}

	const forwarded = request.headers.get("x-forwarded-for");
	if (forwarded) {
		const candidates = forwarded
			.split(",")
			.map((value) => value.trim())
			.filter(Boolean);

		if (candidates.length > 0) {
			return candidates[candidates.length - 1];
		}
	}

	return "unknown";
};
```

Because the endpoint accepts these values directly from the request, the limiter key is attacker-chosen rather than server-derived. The result is a security decision based on untrusted input: once one spoofed address reaches the threshold, switching to a different header value immediately restores access to the pre-limit path. The route then continues into the service-role-backed **`supabase.from("contacts").insert(...)`** operation.

## Proof of Concept

1. Send repeated unauthenticated **`POST`** requests to **`/api/contact`** with a valid JSON body and a fixed spoofed **`X-Forwarded-For`** value.
2. Observe that the first eight requests are processed normally and the ninth request returns **`429`**.
3. Resend the same request immediately, changing only the spoofed forwarding header to a different IP value.
4. Observe that the response returns to a non-**`429`** status, proving the limiter key is derived from attacker-controlled headers rather than a trusted server-side client address.
5. Confirm that the non-**`429`** requests still reach the contact ingestion path, evidenced by downstream processing responses instead of rate-limit rejection.

```python
import json
import requests

url = "http://127.0.0.1:4321/api/contact"
payload = {
    "name": "Test User",
    "email": "test@example.com",
    "message": "This is a validation message for rate limit behavior.",
    "consent": True,
}

headers = {
    "Content-Type": "application/json",
}

for i in range(1, 10):
    test_headers = headers | {"X-Forwarded-For": "203.0.113.50"}
    response = requests.post(url, headers=test_headers, data=json.dumps(payload), timeout=10)
    print("203.0.113.50", i, response.status_code, response.text)

for spoofed_ip in ["203.0.113.51", "203.0.113.52"]:
    test_headers = headers | {"X-Forwarded-For": spoofed_ip}
    response = requests.post(url, headers=test_headers, data=json.dumps(payload), timeout=10)
    print(spoofed_ip, response.status_code, response.text)
```

## Remediation

1. Derive the rate-limit key from a server-trusted client address provided by the runtime or hosting platform, not from raw request headers.
2. For Astro server routes, prefer the framework-provided client address value and fall back to a safe sentinel when it is unavailable.
3. Treat **`X-Forwarded-For`** and **`X-Real-IP`** as untrusted unless they have been sanitized by a specifically trusted reverse proxy under application control.
4. Apply the same rule consistently anywhere the shared IP helper is used for security decisions, including other throttled endpoints.

## Assumptions

Assumes the contact endpoint is publicly reachable and the runtime provides a trustworthy server-derived client address such as Astro's `clientAddress`. The demonstrated impact does not assume successful Supabase writes in the local environment; it is based on confirmed evasion of the limiter and continued access to the protected ingestion path.
